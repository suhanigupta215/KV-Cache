# MTR-KV Presentation Dashboard Design

## Purpose

Build a simple local frontend that helps an evaluator or non-specialist understand what MTR-KV does, why its control protocol matters, and how baseline, codec-only, and full MTR-KV differ. The dashboard is a presentation companion for the deterministic simulator; it does not claim to control a real GPU or decoder.

## Audience and Success Criteria

The primary audience is a college-project evaluator, with technical reviewers and classmates as secondary audiences. A successful screen explains the architecture in under one minute, makes the MTR-KV result categories easy to compare, and preserves traceability to generated simulator output.

## Scope

The dashboard is a dependency-free static web application in `frontend/`. It reads the existing `results/simulation.json` artifact from a browser file picker, includes a built-in example dataset for first use, and does not execute Python or modify simulator configuration. It can therefore be opened locally without a backend or package install.

The visual direction is a dark, spacious presentation dashboard inspired by the supplied reference: charcoal canvas, muted cards, restrained cyan and violet accents, rounded panels, and large readable metrics. It avoids copying the supplied product imagery or Pinterest branding.

## User Flow

1. The opening hero names MTR-KV and describes the system in plain language.
2. A horizontal pipeline explains codec metadata through temporal state, MTRE, MKAD, KMC, transformer feedback, and SRCE semantic rescue.
3. The visitor selects a baseline, codec-only, or full-MTR-KV result mode.
4. Summary cards and a tier-residency chart update from the selected raw metrics.
5. A frame timeline exposes pages avoided, fallback frames, transition prediction, and semantic rescue at each frame.
6. An explanation panel translates the selected mode into evaluator-friendly terms and clarifies that the data comes from a simulator.
7. The visitor can load a fresh `simulation.json` generated by `python -m mtr_kv run`.

## Information Architecture

### Header and Hero

The header holds the project label, a compact safety status badge, a button to load a JSON artifact, and a reset-to-example action. The hero contains the plain-language statement: MTR-KV uses early codec motion evidence to place KV-cache pages in memory tiers, then uses semantic evidence to correct unsafe low-motion assumptions.

### Architecture Pipeline

Six connected cards describe the frozen data path: `Video metadata`, `Temporal state`, `MTRE mapping`, `MKAD descriptor`, `KMC commit`, and `Semantic rescue`. The final two cards explicitly call out generation IDs and `RESERVE → PREPARE → COMMIT → READY` to communicate safety.

### Metrics Workspace

The mode selector controls four primary cards: pages avoided, bytes saved, semantic rescues, and stale drops. A compact horizontal bar chart compares baseline pages with hot pages and total resident pages. The metrics use exact values from the loaded JSON and display `—` where a field is absent.

### Frame Timeline and Explanation

The frame table is rendered from the selected run's `frames` array. It shows generation, pages avoided, T0/T1/T2 residency, rescue count, and state markers. Selecting a row updates a side panel explaining the event in ordinary language. The page retains a static methodology notice: results are simulation measurements, not hardware claims.

## Data Contract

The UI consumes the JSON emitted by `mtr_kv.__main__`:

```json
{
  "config": { "name": "frozen-reference-v1", "version": "1.0" },
  "scenario": { "name": "T03_semantic_rescue", "seed": 20260922 },
  "runs": {
    "full": { "metrics": {}, "frames": [] }
  }
}
```

The parser must validate the presence of `scenario` and at least one run with `metrics`. Invalid JSON or an incompatible file produces an inline error and leaves the last valid dashboard data visible.

## Technical Design

Create `frontend/index.html`, `frontend/styles.css`, and `frontend/app.js`. `index.html` provides accessible semantic landmarks and a hidden file input. `styles.css` owns responsive layout, visual tokens, and motion-reduced styling. `app.js` owns embedded example data, validation, DOM rendering, mode switching, JSON file loading, chart drawing with HTML/CSS, and frame-row selection.

No framework, CDN, network request, build tool, or production server is required. The dashboard runs by opening `frontend/index.html` in a browser. A root `frontend/README.md` describes opening the dashboard and regenerating data.

## Error Handling and Accessibility

The mode selector defaults to the first available run if the requested mode is missing. File loading displays actionable status text for unreadable, invalid, or incompatible JSON. Controls are keyboard reachable, have visible focus states, and use native buttons/selects. Color is not the only signal for state; icons/text labels accompany tier, fallback, rescue, and safety cues. Responsive rules collapse dashboard columns for narrower screens.

## Verification

Manual verification opens the dashboard with the built-in example and then loads `results/simulation.json`. It verifies each mode updates all metrics, the frame selection updates the explanation panel, and an invalid JSON file reports an error while preserving the displayed result. The Python regression suite remains unchanged and must pass after the frontend is added.
